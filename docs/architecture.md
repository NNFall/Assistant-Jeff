# Архитектура Assistant Jeff 0.7

Документ описывает текущий путь `npm start` из `scripts/desktop-lab/main.mjs`. **Jev выбирает маршрут окончательного запроса и каждый следующий шаг управления компьютером.** Gemini распознаёт речь и обслуживает отдельный контур разговора, заметок и напоминаний. Результаты сборки, установки и реальных прогонов фиксируются в [отчёте 0.7](jev-windows-v07.md); наличие ветки в коде не означает её проверку на каждом приложении Windows.

## Основной путь

```text
Renderer: текстовая команда / финальная голосовая транскрипция
                         |
                    VoiceSession
                         |
              JevAssistant: Jev выбирает маршрут
                  /                       \
              desktop                 memory / conversation
                 |                           |
            JevCommands             AgentCommands + Gemini /agent
                 |                           |
       наблюдение → выбор Jev         LocalToolRegistry: только data-tools
                 |                           |
       локальный Windows executor      Store: заметки и напоминания
                 |
       receipt → новое наблюдение
                  \                       /
                 общий report → UI → Denis
```

`JevAssistant` (`desktop/agent/jev-assistant.mjs`) сохраняет интерфейс голосового слоя: `run({command, mode, signal})`, `running`, `activeRunId`, `stop`, `clearContext`, `capabilities`. Он запрашивает один типизированный выбор `desktop`, `memory` или `conversation`. В production последние два маршрута используют один ограниченный экземпляр `AgentCommands`, поэтому уточнения времени и ссылки на предыдущую запись сохраняют контекст. Набор его инструментов создаётся только из `createDataTools({store})`.

Ошибка Jev, неизвестный ID или недостаточная уверенность не передают desktop-задачу Gemini. У data-агента отсутствуют Windows, system, text и winapp executors; ответ модели с таким именем инструмента не может выполнить действие. Gemini Gateway работает для STT и данных, но не является планировщиком desktop-цикла.

## Цикл Jev и запрос решения

`JevCommands` (`desktop/agent/jev-commands.mjs`) владеет одной desktop-задачей. По умолчанию запуск ограничен 24 шагами и 120 секундами. На каждом шаге он:

1. Вызывает `session.observe` и получает компактное наблюдение с доступными кандидатами.
2. Сохраняет запрос в журнал и вызывает `chooseJevStep`.
3. Проверяет выбранный ID и пороги; передаёт ровно один кандидат в `session.execute`.
4. Сохраняет receipt отдельного действия и снова читает текущий интерфейс.

`desktop/providers/jev-step.mjs` отправляет в TypeSafe `model: 'jev-latest'` и один `Choice` — `questions.next_step`. Состояние содержит исходную `command`, текущее `observation`, готовые `candidates`, последние восемь кратких исходов `recentSteps` и, при необходимости, ограниченный `context`. Общая инструкция задаёт следующий доступный шаг и условия завершения; схема не запрашивает свободный план, код или рассуждение.

Кандидат содержит читаемую метку, операцию, признак эффекта и нужные сведения о цели. Исполняемые функции, native-аргументы и полная история голосового разговора в desktop-запрос не попадают. Ответ содержит вариант, распределение вероятностей, confidence, модель, usage и задержку. ID — непрозрачный ключ, который нельзя декодировать или придумывать.

| Решение | Условие выполнения |
| --- | --- |
| Маршрут, действие с эффектом, `done` или `unavailable` | Вероятность выбранного варианта и confidence не ниже 0,8 |
| Дополнительный `inspect` при низкой уверенности | Кандидат имеет `effect: false`; оба показателя не ниже 0,2; не более трёх таких чтений за запуск |
| Неизвестный вариант или несовпадающий executable ID | Исполнение не запускается |

Исключение для чтения помогает раскрыть следующий уровень иерархии. Оно не снижает порог изменения состояния или завершения. Пороги являются политикой приложения, а не гарантией правильности модели.

## Иерархия Windows и связь с исполнением

`createJevDesktopSession` (`desktop/agent/jev-desktop-session.mjs`) создаётся заново для каждой команды. Первое наблюдение сбрасывает ранее выбранное окно и читает доступные поверхности. Затем Jev выбирает чтение конкретного окна, панели задач/трея, обнаруженного меню, другой страницы контролов или каталога программ. Чтение поверхности само по себе не активирует её и не выполняет цель.

Панель задач дополнительно разбивается по наблюдаемым UIA-классам на системный трей, Пуск/поиск и кнопки приложений. Сначала Jev выбирает область, затем получает действия её кнопок. В выбранном окне не смешиваются действия всех остальных приложений; новые системные меню остаются доступны, а к полному списку окон можно вернуться отдельным чтением. Неизвестная реализация панели без структурных метаданных сохраняет обычный список наблюдаемых контролов.

Каждое наблюдение создаёт новую локальную таблицу соответствий:

```text
step_01 → локальный executor + фиксированные аргументы
        → windows_execute(snapshotVersion, native actionId)
        → WindowsBridge → FlaUI/UIA3 helper → native receipt
```

Короткие ID не являются HWND или селекторами. Таблица хранит точное соответствие варианта native-кандидату; после выбора она расходуется, а следующий шаг получает новые наблюдения и варианты. Перед эффектом адаптер перечитывает состояние и проверяет версию окна либо полного UIA-снимка в зависимости от операции. Helper дополнительно проверяет идентичность цели. Устаревшее состояние до эффекта приводит к повторному наблюдению, а не к исполнению старого решения.

Набор вариантов определяется текущей разрешённой UIA-иерархией, а не заранее записанным сценарием для одного приложения. Страницы кандидатов и признаки неполного чтения остаются видимыми модели. Частичный порядок вкладок не может подтвердить «первую» или «последнюю» во всей группе. Каталог приложений даёт фиксированный путь запуска; числовые варианты громкости извлекает код из команды, а Jev выбирает применимый вариант. UI-текст и названия устройств являются данными наблюдения и не дают отдельного разрешения.

У действия есть устойчивый ключ для контроля повторов, отдельный от короткого ID. Подтверждённый dispatch без конечного postcondition требует нового наблюдения; неопределённый эффект останавливает запуск. Уже отправленное действие не повторяется вслепую. Если native-вызов продолжает работать после отмены, single-flight блокировка сохраняется до завершения его promise, даже когда отчёт о неопределённости уже возвращён.

## Native helper и границы покрытия

Текущий desktop-executor — C# helper на FlaUI/UIA3 через `WindowsBridge` и `windows-tools.mjs`. Он читает разрешённые окна приложений и системные поверхности, предоставляет фиксированные операции и возвращает состояние после действия. Для Windows Shell проверяется идентичность системного процесса/поверхности; одного названия окна недостаточно. CoreAudio используется для громкости и чтения фактического аудиовыхода.

В helper предусмотрен ограниченный `click` для разрешённых наблюдаемых кнопок Windows Shell. Native-код получает точку из свежего UIA-элемента, проверяет bounds, идентичность и попадание в тот же элемент, затем выполняет click. Jev выбирает готовый кандидат и не передаёт координаты. Эта ветка нужна кнопкам, у которых Invoke не открывает интерфейс, но её наличие не подтверждает работу каждого shell-меню. Проверенные native-сценарии и ограничения фиксируются в [отчёте 0.7](jev-windows-v07.md).

UIA helper включает PerMonitorV2 до чтения геометрии и работы с мышью. Click доступен только при подтверждённом физическом пространстве координат. После одного shell-нажатия выполняются пассивные повторные чтения в ограниченном бюджете ожидания меню; повторного нажатия этот цикл не делает. В receipt сохраняются число чтений и затраченное время.

Microsoft `winappCli v0.6.1` остаётся в runtime-пакете, а `desktop/agent/winapp-tools.mjs` — в исходниках. Это прежний адаптер, **не подключённый к текущему desktop-исполнителю**. Отдельный путь `windows_text_fields` / `windows_text_replace` также сохранён, но не зарегистрирован в новой сессии Jev. Прежние `WindowsDesktop.run`, `windows_choose` и `UnifiedCommands` не определяют основной цикл 0.7; объект `WindowsDesktop` предоставляет bridge, каталог программ и запуск приложения.

Покрытие зависит от UIA-провайдера, прав процесса, видимости элементов, виртуализации и interactive desktop. Canvas без accessibility, закрытая сессия и окна с более высоким уровнем прав могут оставаться недоступными. Скриншоты не анализируются моделью; OCR/vision-пути здесь нет. Наблюдение разрешённой иерархии не означает универсального управления каждым Windows-контролом. Произвольные shell-команды, сгенерированные селекторы и точки экрана не входят в контракт модели.

## Подтверждение действия и всей задачи

Receipt содержит `ok`, `verified`, `effectAttempted`, `status` и evidence. Успешное чтение не является эффектом. Подтверждённое уже достигнутое состояние тоже не записывается как новая мутация. `invoke` или `click` с наблюдаемым изменением интерфейса подтверждает отдельный dispatch, но не весь смысл запроса.

Финальный отчёт разделяет:

- `goal_verified` / `goalVerification: native_verified`: применимый локальный verifier подтвердил конечное состояние. Например, для узкой команды выбора явно названного аудиоустройства перечитывается фактический default endpoint. Подтверждение одного аудиопункта не подтверждает дополнительные части составной задачи.
- `goal_model_assessed` / `goalVerification: model_assessed`: Jev выбрал `done` с достаточными показателями по текущим фактам и результатам, но отдельного полного native-verifier для задачи нет.
- `execution_uncertain`, `goal_not_verified` и другие остановки: совершённые и частичные эффекты остаются в отчёте. Отсутствие итогового успеха не означает отсутствия изменений.

Доказательства отдельных эффектов хранятся отдельно от оценки конечной цели. Интерфейс и Denis передают это различие: `ok` или одно изменение UI не заменяют проверку всей задачи.

## Данные, Gemini и контекст

`AgentCommands` (`desktop/agent/commands.mjs`) сохранён для разговора, заметок и напоминаний. `GeminiGateway` передаёт типизированные `contents`, `tools` и небольшой `context` в `/agent`; `server/agent-model.mjs` валидирует запрос/ответ. Gateway не читает SQLite и не выполняет Windows-действия. LocalToolRegistry этого контура содержит только `createDataTools` и финальный `assistant_respond`.

Заметки поддерживают поиск, чтение, создание, изменение и удаление; напоминания — также завершение. Изменение или удаление требует чтения цели в текущем запуске и точного `expectedText`, для напоминания — ещё `expectedDueAt`. После записи Store перечитывается. `clock_now` сообщает время, а `time_resolve` рассчитывает срок из явных компонентов; отсутствующий день или час становится уточнением.

История data-агента ограничена восемью ходами, 24 KiB и TTL 30 минут. Роутер Jev использует до четырёх кратких предыдущих запросов/ответов с тем же TTL, чтобы понимать ссылки и ответы на уточнения. UI-снимки и action IDs между desktop-задачами не переносятся. История является справкой, а не новым разрешением. `clearContext` работает в простое; остановка очищает контекст.

`assistant_respond` остаётся единственным финальным function call data-агента. Для `completed` нужны ID проверенных receipts; `answer`, `clarification` и `incomplete` обозначают другие результаты. Gemini этого контура не получает Windows-tools ни для нового запроса, ни для продолжения разговора.

## Голос и озвучка

`VoiceSession` остаётся общей границей текстовых и голосовых команд. Локальный openWakeWord ждёт Hey Jarvis; облачное распознавание начинается после активации или явной записи. Основной путь — Gemini 3.5 Transcribe Live: PCM16 mono 16 kHz, буфер примерно на две секунды во время подключения и завершение реплики после двух секунд тишины. Резервный batch-путь использует MP3. Desktop-модель Jev не заменяет эти компоненты.

Промежуточная транскрипция служит только для отображения. Лишь окончательный текст при разрешённом auto-execute попадает в `JevAssistant`; иначе он остаётся для редактирования и явного запуска. Поздние события отменённой операции отбрасываются. Текстовая команда не включает микрофон.

Denis остаётся локальным Piper-голосом. Он озвучивает итоговый report с подтверждениями и ограничениями; ошибка TTS не меняет результат уже выполненной задачи. Stop прекращает дальнейшие действия и озвучку, сохраняя сведения о совершённых эффектах.

## Журналы и интерфейс

Renderer использует ограниченный preload API с `contextIsolation`, sandbox и отключённой Node integration. Контроллеры, registry и native helper работают из Electron main. Ключи остаются в DPAPI текущего пользователя и серверной конфигурации; в renderer они не передаются. Пользовательская SQLite сохраняет прежнюю схему и не заменяется обновлением контроллера.

Родительский журнал `JevAssistant` содержит выбор маршрута и роль провайдера. Дочерние события desktop/data-контроллера объединяются в его `events`/`trace` с родительскими `runId` и `sequence`; исходные значения сохраняются в `sourceRunId`, `sourceSequence`, `sourceTime`. Это сохраняет связь evidence IDs с receipts и отделяет маршрут от исполнения. Для live-прогресса main сопоставляет дочерний ID активной родительской задаче.

Запрос модели и запись перед эффектом должны успешно попасть в журнал до исполнения. Ошибка записи останавливает дальнейшие эффекты. Сохраняются нормализованные решения, вероятности/confidence, usage, операции, receipts и итог, но не секретные заголовки, скрытые рассуждения или необработанные opaque signatures. Тексты команд, заметок и видимых UI-меток могут входить в журнал. PCM/MP3-байты и interim-гипотезы голоса не сохраняются.

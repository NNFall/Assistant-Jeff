# Jev: проверка общего и ограниченного набора Windows-действий

21 сентября 2026, начало 18:20:43 UTC / 22:20:43 Самара. Исходный runtime — Assistant Jeff 0.6.0, commit `b006b788b9cd909101ce58da0c0b682f02ef131f`.

**Убедительного улучшения от одного сокращения списка кандидатов не получено.** На заранее подготовленных синтетических русских примерах общий профиль дал 16/28 совпадений с ожидаемым решением, ограниченный — 17/28. При неполном порядке вкладок оба профиля уверенно предложили неверно обоснованное действие. Это реальный API-замер выбора, без управления компьютером.

## Что сравнивали

- Модель: закреплённая `jev-1.13.0`; все 56 ответов подтвердили именно эту версию. Production builder остаётся на `jev-latest`: версия закрепляется только в отправляемом evaluator запросе.
- 14 размеченных до запуска случаев × 2 профиля × 2 повтора = **56 последовательных HTTP-вызовов**. Порядок full/scoped чередуется между случаями и меняется во втором повторе. Retries отсутствуют, жёсткий максимум — 64 вызова.
- `full`: полный заданный в fixture список. `scoped`: все кандидаты заранее подготовленной операции плюс все `inspect`. Для запрета и цитаты остаётся весь исходный набор.
- Команда, наблюдаемые факты, история, production instructions и пороги одинаковы. Фильтр не смотрит на ожидаемый ID, не выбирает окно за Jev.
- **Тип операции задаётся извне вручную.** Мы не проверяем, умеет ли модель сама выделить подзадачу. Это небольшие подготовленные наборы, а не снимки настоящего Windows adapter: 4–6 кандидатов в full, 3–5 в scoped. «Десятки отвлекающих окон» этот замер не моделирует.
- Использованы настоящий `buildWindowsChoiceRequest`, нормализация ответа `chooseWindowsAction` и оба текущих порога: probability ≥0,8 и confidence ≥0,8. Для `done` дополнительно необходимы goal_status=achieved и оба порога второй независимой оценки.
- Никаких shell-команд, кликов, чтения пользовательских окон, микрофона или личной базы. Ключ прочитан из существующего DPAPI-файла, в отчёт не попадает.

Набор после результатов не перенастраивался и повторно ради лучшей цифры не запускался. Ошибка закрепления модели в первоначальном evaluator исправлена и покрыта offline integration-тестом до live-запуска.

Это метрика ожидаемого решения selector, **не процент успешно выполненных Windows-команд**. Ошибочная остановка может быть безопасной, но плохо объяснённой: например, при двух одинаковых заголовках действие было заблокировано, однако модель выбрала inspect вместо ожидаемого unsupported. `unsupported` и `no_request` оцениваются как семантически правильный отказ без требования порога; они не разрешают действие. Для `done` пороги обязательны. Совпадение следующего действия не оценивает всю семантику второго head: например, у цитаты модель выбирала правильный no_request, но goal_status=not_achieved вместо ожидаемого по prompt unknown.

Одна дополнительная удача из 28 — недостаточное основание считать scoped надёжнее. Медиана latency не улучшилась; первый full-запрос 2040 мс сохранён в статистике, причина его задержки не установлена. p95 рассчитан линейной интерполяцией. Снижение входных токенов — около 3,1%: общий длинный prompt остался тем же.

Всего использовано 227 488 входных и 7146 выходных токенов. По опубликованной цене Jev $0,042 за миллион входных токенов и бесплатному output расчётная стоимость inference — около **$0,00955**. Это расчёт по [публичному тарифу](https://docs.typesafe.ai/models), не платёжная квитанция и не стоимость всей голосовой команды.

## Пример фактического входа и выхода

Для `chrome_minimize_simple`, первый full-запрос, модель получила нижеуказанное состояние плюс неизменные production instructions и два Choice-вопроса. Это сокращённое представление входа; полный JSON включает описания всех кандидатов и обеих оценок.

```json
{
  "model": "jev-1.13.0",
  "state": {
    "command": "Сверни окно Chrome.",
    "observation": {
      "app": "Windows desktop",
      "summary": "Chrome — «Документация» выбран, видим и не свёрнут; Edge — «Новости» и Slack — «Команда» видимы рядом."
    },
    "phase": "controls",
    "completed": []
  }
}
```

Шесть кандидатов: свернуть Chrome, свернуть Edge, активировать Chrome, осмотреть Chrome, осмотреть Edge, закрыть Chrome. Каждый имеет fixed ID, label и operation. Сам список и тексты критериев генерирует код; Jev не создаёт новые команды.

Фрагмент **фактического нормализованного результата** (это вывод нашего adapter, не выдуманный текст рассуждений модели):

```json
{
  "choice": "chrome_minimize_docs",
  "actionId": null,
  "probability": 0.78,
  "confidence": 0.75,
  "goalStatus": "not_achieved",
  "goalProbability": 1,
  "goalConfidence": 0.99,
  "model": "jev-1.13.0",
  "usage": { "input_tokens": 4190, "output_tokens": 147 }
}
```

То есть нужное действие оказалось первым выбором, но исполнитель не получает разрешённый actionId, потому что оба порога не пройдены. Этот пример объясняет механизм «понял название, но не выполнил», однако не восстанавливает причину какого-либо конкретного старого пользовательского запуска.

Второй важный пример: у `partial_tab_coverage` первый full-запрос вернул `choice=vk_tab_news`, `actionId=vk_tab_news`, probability=0,96, confidence=0,95. Наблюдение прямо сообщало `partial coverage`. Высокая уверенность не проверила предпосылку «это действительно первая среди всех вкладок». Во втором профиле confidence оставался 0,91 в обоих повторах. Никакое действие физически не выполнялось.

## Что следует менять дальше

1. Предпосылки вроде полного порядка вкладок, идентичности цели и актуальности наблюдения проверять программно. Не давать модели единолично разрешать их по confidence.
2. Отдельно испытать более короткий контракт одной подзадачи и качественное выделение её из свободной команды. Нынешний эксперимент менял только кандидатов и не проверял полный подход arc-cua.
3. Измерять факт достижения цели и весь цикл от финальной речи до проверенного эффекта. Одна модельная задержка около 0,34 с не превращает многошаговую команду в задачу на 0,34 с.
4. Оставить возможность остановки и возврата к общему агенту. Снижение единого порога не устраняет уверенные неверные выборы; в этом прогоне они уже выше 0,9.

Дополнительно статически проверен путь AgentCommands 0.6: `desktop/automation/windows-candidates.mjs` добавляет `orderIsPartial` в описание, сохраняя select при наличии capability; `desktop/agent/windows-tools.mjs` проверяет membership/freshness/receipt, но отдельного запрета ordinal-выбора по неполному порядку не содержит. В `native/windows-desktop/Helper.cs` native Select проверяет выбранное состояние, а не соответствие слову «первая». Поэтому нельзя считать, что сама запись `partial` уже защищена независимым предусловием.

Это конкретный пробел контракта, который нужно закрыть на уровне общего разрешения цели: различать выбор по имени/ID и выбор по порядку, требовать полное покрытие нужной группы именно для ordinal-выбора. Запрет всех select на любой неполной странице был бы чрезмерным — выбор известного по имени элемента не обязательно зависит от порядка.

Эксперимент остаётся проверкой selector на подготовленных данных. Он не доказывает реальный ошибочный клик в установленной версии: настоящие UIA facts, полный путь выбора, freshness и receipt здесь не воспроизводились. Установленное приложение этой исследовательской правкой не обновлялось.
